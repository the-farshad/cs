If an array is **sorted**, you can find any value without scanning it. Look at
the middle element: if it is your target, done. If it is too small, the target
must be to the right; if too big, to the left. Either way you throw away **half**
the array and repeat.

Pick a target and step through it. The shaded boxes are the part of the array
still in play; the amber box is the `mid` being checked.

## The invariant

Binary search keeps a window `[lo, hi]` with one promise: *if the target is in
the array at all, it is inside this window.* Each step checks the midpoint and
shrinks the window to the half that can still contain the target. When the window
is empty, the target was never there.

## Why O(log n)

Every step halves the window. Starting from `n` elements you can only halve
about `log₂ n` times before nothing is left. So a million-element array takes
about 20 steps, and a billion takes about 30. That is the power of logarithmic
time.

## Common pitfalls

- **Off-by-one:** decide whether `hi` is the last valid index (`lo <= hi`) or one
  past the end (`lo < hi`), and stay consistent.
- **Midpoint overflow:** in fixed-width integer languages, `(lo + hi)` can
  overflow — prefer `lo + (hi - lo) / 2`.
- **It needs sorted input.** On unsorted data the invariant is false and the
  result is meaningless.

## Takeaways

- Sorted data unlocks logarithmic search — a massive win over linear scanning.
- The whole method is one invariant plus "halve the range."
- The same halving idea generalizes: it is how you binary-search on answers, not
  just arrays.
